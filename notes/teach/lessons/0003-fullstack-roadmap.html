Fullstack Roadmap -- Build & Ship

Your curated path from where you are (strong CS foundations) to a shipped fullstack product and startup-ready portfolio. Read this first; it drives every stage lesson.

Method: watch the ONE video per stage -> build the stage project -> learn gaps on demand. Not tutorial hell: 1 hr video : 3 hr building.

Who this is for (you) You have A's in Python, OOP/Java, DSA, computer org, databases. You're past "learn to program." Your gap is building glue (frameworks, APIs, deploy) + JS-native concepts. This plan skips what you know and attacks only those two gaps.
The North Star The goal is not "finish a curriculum." It's ship a real product people use. Every stage ends in a build. By Stage 5 you have a deployed fullstack app -- that's your portfolio centerpiece and your startup-interview ticket.

What we SKIP (and why)

Deliberate omissions HTML/CSS deep dives (you have enough to build UIs) · DSA / DB theory / OOP theory (coursework done; DSA is a separate interview track) · TypeScript (add after first ship) · Docker / K8s / CI-CD / Nginx (enterprise devops, learn on the job) · Redis / queues / GraphQL / microservices (premature for an MVP) · Vue / Angular / Mongo (pick React + Postgres). Each skip is either known or learn-when-a-project-demands-it.

STAGE 1 JavaScript (deep on JS-native) ⏱ ~2-3 wks

The hinge of everything -- React is 70% JS, Node IS JS. Skim the parts that match other languages; go slow on the JS-native parts: closures, this, prototypes, async/event loop, the DOM.

▶Learn JavaScript (interactive full course)freeCodeCamp / Scrimba -- opens YouTube

Supplement per-concept with Web Dev Simplified (one clean video each for closures, the event loop, fetch). For depth on the weird parts, Fireship "JavaScript in 100 Seconds" + its deeper cuts.

Gotchas the videos gloss over • == vs === -- always use === (no type coercion surprises).
• var is dead -- use const by default, let when reassigning. var is function-scoped + hoisted = bugs.
• this is decided by HOW a function is CALLED, not where it's defined. Arrow functions don't bind their own this -- that's why they're used for callbacks.
• Closures aren't academic -- every event handler / callback that "remembers" a variable IS a closure. You'll use them constantly.
• Async isn't parallel -- JS is single-threaded; the event loop just defers work. await pauses the function, not the program.
• const arr = [] then arr.push() works -- const locks the binding, not the contents.
Ship this stage A small JS app with no framework: fetch from a public API (weather, movies, GitHub) and render results to the DOM with user input. Forces fetch + async + DOM + events together. (Steal Odin's "Weather App" spec.)

STAGE 2 React (the user-facing layer) ⏱ ~2 wks

This is where "users see your stuff" lives. Learn the floor: components, JSX, props, state (useState), effects (useEffect), events, forms, conditional rendering, lists, and basic routing. Stop before context/reducers/perf -- add those when a project needs them.

▶React 19 Full Course -- build an app in ~2 hrsopens YouTube 📚react.dev -- the OFFICIAL tutorial (use over randoms)react.dev/learn
Gotchas the videos gloss over • State is immutable -- never mutate then set. Make a new object/array: setItems([...items, x]), not items.push(x).
• State updates are async + batched -- reading state right after setState gives the OLD value. Use the updater form setX(prev => ...) when depending on previous.
• useEffect runs after render; the dependency array controls when. Empty [] = once on mount. Missing it = every render (common infinite-loop bug).
• Every list item needs a stable key -- index-as-key breaks on reorder.
• A component re-renders when its state/props change -- that's normal, not a leak.
• JSX is JS -- className not class, {expression} for dynamic values.
Ship this stage Rebuild your Stage 1 app's frontend in React, OR build a CRUD UI (a task/notes/bookmark app) with add/edit/delete + a form. Deploy the frontend to Vercel/Netlify (free, ~5 min).

STAGE 3 Node + Express (your backend) ⏱ ~2 wks

Server-side JS. Learn: the Node runtime basics, npm, Express routing, middleware, REST verbs (GET/POST/PUT/DELETE), route params, request/response, JSON, error handling, CORS. This is where your OOP/DSA foundation pays off -- the logic is familiar, only the framework is new.

Gotchas the videos gloss over • Middleware order matters -- Express runs them top-to-bottom; app.use(express.json()) must come BEFORE routes that read req.body, or body is undefined.
• CORS will block your React frontend from calling your API on a different port -- add the cors middleware early (a day-one confusion for everyone).
• Always handle async route errors (try/catch or a wrapper) -- an unhandled rejection can hang the request.
• Never put secrets/DB URLs in code -- use .env + dotenv, and gitignore it.
• A REST API returns JSON, not HTML -- the frontend renders; the API serves data.
Ship this stage Build a REST API for your CRUD app (in-memory data is fine first). Connect your React frontend to it via fetch. Now you have a real client-server app talking over HTTP.

STAGE 4 PostgreSQL + Prisma (data that persists) ⏱ ~1-1.5 wks

You know SQL (CSC365) -- this is mostly the wiring. Prisma is an ORM: define your schema, it generates a type-safe client so you query the DB from JS without raw SQL strings. Learn: schema/models, migrations, relations, CRUD via Prisma client, seeding.

▶Prisma ORM Full Course 2025opens YouTube
Gotchas the videos gloss over • Migrations are not optional -- every schema change = prisma migrate dev. Editing the DB by hand desyncs Prisma.
• Your CSC365 SQL still matters -- Prisma generates SQL, but you debug performance by reading it. Know your indexes/joins.
• Use a real Postgres early (Neon/Supabase free tier) so dev matches prod -- SQLite-in-dev then Postgres-in-prod causes surprises.
• Connection limits on free tiers are low -- use a single Prisma client instance, don't instantiate per request.
Ship this stage Swap your API's in-memory data for Postgres via Prisma. Data now survives restarts. This is a genuine fullstack app: React -> Express -> Prisma -> Postgres.

STAGE 5 Auth + Deploy (make it real) ⏱ ~1.5 wks

The two things that turn a demo into a product: users can log in, and it's live on the internet. Learn: password hashing (bcrypt), sessions or JWT, protected routes; then deploy frontend + backend + DB.

Gotchas the videos gloss over • NEVER store plaintext passwords -- always hash with bcrypt. This is non-negotiable and interviewers ask.
• JWT vs sessions: JWT for stateless APIs, sessions for traditional server-rendered. Either is fine for an MVP -- pick one, don't agonize.
• Env vars differ per environment -- your prod DB URL + secrets go in the host's dashboard, never in git.
• Set CORS to your real deployed frontend domain in prod (not *).
• Deploy EARLY and often -- "works on my machine" hides a dozen prod-only bugs. Deploy a hello-world first, then iterate.
Ship this stage = THE milestone Add login to your app, deploy all three layers, put the live URL on your resume/GitHub. Get 5-10 real users (friends count). You are now application-ready.

After Stage 5 (when, not now)

The "next" pile TypeScript (add types to your project) · Next.js (SSR, the startup default) · testing (Jest/Vitest) · a second, more ambitious product. By here you'll know what your project actually needs -- learn those on demand, not preemptively.
The two parallel tracks This roadmap is the BUILD track. Run a light DSA track alongside (~3-4 LeetCode/week in Java) for interviews -- startups weight it less than big tech, but it's still the gate. Build track gets you the portfolio; DSA gets you through the loop.
